# ADR-0004. Консистентность бронирования: остатки, идемпотентность, outbox

**Статус:** принято

## Контекст
Бронирование работает с деньгами и ограниченным ресурсом (номера на дату). Нельзя:
продать последний номер дважды, списать деньги дважды при повторе запроса, потерять событие
«бронь подтверждена», если брокер сообщений недоступен.

## Решение

**Остатки без овербукинга.** Таблица `room_inventory (rate_id, stay_date, allotment, booked)`.
Резерв — условный `UPDATE ... SET booked = booked + 1 WHERE booked < allotment` по всем ночам;
если обновилось меньше строк, чем ночей, — исключение и откат. В READ COMMITTED конкурентный UPDATE
ждёт блокировку строки и перечитывает условие — второй претендент на последний номер получает 409.
Страховка на уровне схемы — `CHECK (booked <= allotment)`. Без распределённых блокировок и Redis.

**Удержание с таймером.** Бронь создаётся в статусе `HELD` на 15 минут. Фоновая задача снимает
просроченные удержания через `SELECT ... FOR UPDATE SKIP LOCKED`: строки, которые прямо сейчас
оплачиваются, пропускаются, несколько экземпляров приложения не мешают друг другу.

**Оплата.** Строка брони блокируется (`PESSIMISTIC_WRITE`) на время оплаты, статус проверяется
до обращения к шлюзу. Отказ банка — штатный исход (402), а не исключение: транзакция коммитится,
номер остаётся за гостем.

**Идемпотентность.** Изменяющие запросы требуют `Idempotency-Key`. Ключ вставляется в
`idempotency_record` в той же транзакции, что и операция: повтор получает сохранённый ответ
(`Idempotent-Replayed: true`), параллельный дубль ждёт на уникальном индексе, упавшая операция
откатывает и ключ. Тот же ключ с другим телом — 422.

**Transactional outbox.** События (`BookingConfirmed`, `BookingCancelled`, `BookingExpired`)
публикуются через Spring Modulith Event Publication Registry: запись о событии сохраняется в
`event_publication` в транзакции брони, затем событие уходит в Kafka (`@Externalized`, топик
`onestep.bookings`, ключ — номер брони, поэтому порядок событий одной брони сохраняется).
Недоставленные события переотправляются по расписанию и при рестарте.

## Последствия
- Корректность держится на гарантиях PostgreSQL, а не на коде приложения — её проще доказать тестом
  (`BookingFlowIntegrationTest.parallelHoldsNeverOverbook`).
- Доставка в Kafka — at-least-once: потребители должны быть идемпотентны по `bookingId`.
- В демо платёжный шлюз — заглушка. В продакшене вызов провайдера выносится из транзакции:
  payment intent + webhook, а статус брони меняется по событию провайдера.
